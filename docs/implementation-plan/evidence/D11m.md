# D11m – Dokumentidentität in CadSession

Status: Windows vollständig geprüft; D11m-FreeBSD-Freigabe und -Abnahme ausstehend.
D11 bleibt `in-progress`. Prüfbasis: `49ac812`, 16.09.2026.

## Lebenszyklusvertrag

CadSession besitzt jetzt eine DocumentId und liefert mit `identifiedSnapshot()`
einen unveränderlichen Snapshot der aktuellen Modellparameter samt ID. Die einzelne
ID ist Sitzungsmetadatum, kein zweiter veränderlicher Dokumentinhalt. ModelDocument
bleibt die einzige Parameterautorität. `documentId()` erlaubt die direkte Abfrage.

| Aktion | Identität und Zustand |
| --- | --- |
| Sitzung konstruieren | Neue zufällige, nichtleere DocumentId |
| Bearbeiten, Undo, Redo | ID bleibt erhalten |
| Wertkopie einer Sitzung | ID bleibt erhalten; keine implizite Duplikatsemantik |
| Save / Save-As | ID bleibt in der laufenden Sitzung erhalten |
| New | Neue ID; leeres, sauberes Dokument ohne Dateipfad und Historie |
| Erfolgreiches Legacy-Open | Neue ID für diesen Import; gespeicherte Parameter bleiben erhalten |
| Fehlgeschlagenes Open / Save | Bisherige ID, Inhalt und gültiger Zustand bleiben erhalten |
| `duplicateDocument()` | Neue ID, identischer Inhalt und Vergabezähler; ohne Pfad, ungespeichert/dirty, ohne Undo-/Redo-Historie |

VOLUND 1–16 enthält keine DocumentId. Deshalb erzeugt auch wiederholtes Öffnen
derselben Legacy-Datei jeweils eine neue ID. Es gibt weder Pfad-Hash noch globale
Pfadzuordnung noch eine still ergänzte Sidecar-Datei. Save-As bewahrt die aktuelle
Sitzungs-ID, kann sie im unveränderten VOLUND-16-Format aber nicht dauerhaft sichern.
Native Wiedereröffnung mit erhaltener ID bleibt bis zum D13-Dispatch offen.

## Veröffentlichung und Fehlergrenzen

New und Open erzeugen ID und vorbereitete Modellwerte vollständig vor dem Austausch
des aktiven Zustands. Die Zufallsvergabe nutzt die bestehende D11e-Implementierung;
ein Fehler bei Vorbereitung/Entropie darf keine teilweise neue Sitzung veröffentlichen.
Die neue ID wird wie andere vorbereitete Werte ohne Allokation übernommen.

Duplizieren erstellt einen Snapshot mit neuem Namensraum und daraus einen neuen
ModelDocument-Wert. Parametergleichheit erlaubt, Auswertung, Körper-/Featurewerte
und Auswahl weiterzuverwenden. Generation und Geometriestempel werden gemeinsam
angepasst; zuvor veraltete Geometrie wird dabei niemals als aktuell markiert.
Dateipfad, Importbericht und sauberer Speicherstand werden zurückgesetzt. Der
Vergabezähler bleibt erhalten, während die flüchtige Historie entfällt.
Generationsüberlauf wird vor der Mutation erkannt.

`duplicateDocument()` ist eine Anwendungsschnittstelle, noch keine neue Desktop-
Aktion. Eine Duplikation nimmt weder einen Dateinamen an noch schreibt sie eine
Datei. Ein nachfolgendes Save verwendet den bestehenden atomaren Dateischreibweg.

## Regressionen

Neuer Test `application.document_identity` prüft:

- Unterschiedliche neue Sitzungen; Wertkopie bleibt im selben Namensraum.
- Bearbeiten, Undo/Redo, Save und Save-As erhalten die Identität.
- Injizierter Speicherfehler und beschädigte Eingabedatei erhalten ID und Zustand.
- Wiederholtes Legacy-Open erzeugt neue IDs bei unveränderten Parametern.
- Duplikat behält Parameter, Auswahl und gültige Geometrie, besitzt neue ID,
  neuen Generationsstempel, keinen Pfad/Importbericht/Undo-Stack und ist dirty.
- Speichern des Duplikats behält dessen ID; New und leeres Duplikat funktionieren.
- Generationsüberlauf für New/Open/Duplizieren lässt den Snapshot unverändert.
- Duplikation eines editierbaren Geometriefehlers erhält die fehlerhaften Parameter
  und verhindert die Beförderung alter Geometrie zum aktuellen Ergebnis.

Die vorhandenen Tests zu Entropie-/ID-Erzeugung, atomarem Store, Transaktionen,
Historie, nativen Snapshots und UI laufen in der vollständigen Suite weiter.
Kein neues natives Schema, kein weiterer Writer, kein Wechsel der Modellautorität.

## Nächster Schritt und offene Abnahme

D11 bleibt offen: Die Dokument-ID ist jetzt in der Anwendung vorhanden, aber noch
nicht über produktives natives Save/Open dauerhaft. Desktop-Duplikataktion und deren
Bedienabnahme fehlen. Als nächster begrenzter Block: explizites Duplizieren an den
bestehenden Desktop-Dokumentablauf anbinden, einschließlich Umgang mit ungespeicherten
Änderungen; keine zweite Befehls-/Dokumentautorität einführen. Den verbleibenden
Persistenzteil ausdrücklich D12/D13 zuordnen und D11-Abschluss danach bewerten.
Der direkte Mehrkörperworkflow A-BODY-03 bleibt getrennt offen (S03/M01–M04/R01).
Basisversion `0.1.0`, Produktwriter VOLUND 16, Meridian L07 unverändert.
